## Session `726ef4ff` — lane `render-web-request-path` — web's ~90s restart loop

### THE QUESTION AND THE ANSWER

Asked: "evaluate if anything needs to change for faster cold boots / avoiding
intermittent 502s". **Cold boot was never the problem.** Boot-to-listening on web
measured **2.7s** (17:12:52.36 `sh -c` → 17:12:55.09 `Listening at` → 17:12:58.43
first `/healthz` 200). There is nothing there to speed up.

The 502s were the process being **SIGTERM'd every ~90 seconds** and ~15s of no
listener after each. On container `-2mdsk` (booted 17:12:55, no deploy after
17:12:59): terms at **17:14:08 / 17:15:38 / 17:17:38**, a NEW gunicorn master pid
each time. Health checks went unanswered for **84s** (17:16:34 → 17:17:58)
straddling the last one. Every request in those windows is a Render 502 — all
carrying `responseBytes=223158`, Render's own error page, which is how you tell
them apart from an app-generated error.

### ROOT CAUSE, IN ONE LINE

`_mlb_feed_live_payload` reads `raw_feed_live_path()` and falls through to
statsapi when it misses. On web it **always** misses: `mlb_source/source_artifacts/
data/raw/statsapi/feed_live/**` matches **none of the 175** `HOT_ARTIFACT_PATTERNS`
(the only `/raw/` entries are NHL's `player_game_stats.csv`). So every home request
made up to 15 live HTTPS calls to statsapi.mlb.com, uncached. Eight request slots
(`WEB_CONCURRENCY=2` × `GUNICORN_THREADS=4`), 3–8s each, and `/healthz` cannot be
answered inside Render's 5s timeout.

`8a7b2407` had shipped `MLB_GAMES_STAGE_MS` for exactly this question and nobody
had read it. It settles two hypotheses at once — **both wrong**:
`per_game_reco_rows` (the scope doc's suspect) was **0–13ms in every sample**, and
`build_cards_page_context`'s live-lens cache-key invalidation (its follow-up
suspect) was not the cost either.

### THE DEAD END THAT MATTERED — allowlisting `feed_live`

The user asked for it explicitly and it would have been a **regression**:

- `_mlb_feed_live_payload` takes the file if it EXISTS, **no freshness check**. So
  publishing it freezes every game at capture time. `board_enrichment.attach_live_
  game_state_from_lens` measured exactly that on 2026-08-13 (`#413`): MIL @ SD
  reading `live / TOP 9` against a lens reading Final; CLE @ DET `BOT 1` two hours
  after first pitch.
- It would also have bought **no speed**: `vendor/mlb_bettingv2/tools/daily_update.py`
  refreshes those files **prior-day only**, with the reason inline — "Prior-day
  reconciliation must fetch the final game feed, not a stale pregame cache entry."
  A freshness gate would reject them and fall through to statsapi anyway.
- Cost ~3.2 MB × 15 = ~48 MB per publish cycle (`cards.py:5803`) against a 2 GB/hr
  publisher brake that exists because outbound hit 1.62 TB in a month.

**Read the consumer before allowlisting a producer.** An artifact that reaches a
service changes what that service's reader DOES, and a reader with no freshness
check turns a latency fix into a correctness bug.
