occurrences that happened to be whole-file deletions.

unreachable. The fix is to gate on the staged BLOB rather than on name-status:
block when a staged blob equals `git ls-tree HEAD^ -- <path>`, or more generally
when the staged content drops lines that are in HEAD and in the worktree.

## UI probe settle — fixed so a plateau cannot report as a finished render

### What was wrong

`_settle()` returned `settled: true` after **two consecutive equal fingerprints**
(800ms, its floor). That is a gate on the *absence* of change, and absence cannot
distinguish "the render finished" from "the render has not started" — they are
the same observation. This is `learnings.md` 2026-08-16, *"a wait loop must gate
on an AFFIRMATIVE success token, never on the absence of a failure string"*,
recurring in a render poll rather than a deploy waiter.

Replaying the old rule over a plateau-then-growth tape:

    old_settle([100,100,100,200,300,400,...]) -> settledMs 800, settled true,
                                                 finalFingerprint 100

It stops inside the plateau and reports the **pre-enrichment DOM as final** while
the render goes on to 400.

### What changed in `scripts/ui_layout_probe.py`

1. **The quiet window is wall-clock, not a poll count.** New `SETTLE_QUIET_MS =

## Desktop height model — it cannot fit, and now it says so

Lane `ui-probe-desktop-height-model`. Asked to make the desktop model fit. It

### Both opening hypotheses were wrong

Written into the lane before testing, then killed by measurement:

- **(a) grid row-stretching** — dead. Every card sits at `left=4`, one per row.
  There is no row to equalise against.
- **(b) two-column wrap** — dead as stated. The pair grid is **10 visible

### What actually drives desktop height: text wrap

Production MLB, 2026-08-16, one slate, one instant, 15 Preview cards. Cards with
**identical** pair counts still differ in height:

| | desktop | mobile |
|---|---|---|
| u=45 (n=7) | 1092..1208 = **116px** | **81px** |
| u=49 (n=5) | 1106..1203 = **97px** | **40px** |

The summary grid is a wrapping flow, so a long team name or a 5-character price

and visible row count still spread **74px** on desktop. `visRows` alone is worse

`reliable` wants `residual <= 0.25 * explained`. A 116px floor therefore needs
**464px** of explained range. Desktop's content spans **197px** (16.4px/pair).
No slope and no intercept reach that. Moving the threshold would manufacture a
fit, not find one.

**And the same measurement reframes the model that passes.** Mobile's residual is
**81px** and its floor is **81px** — the fit sits exactly on the noise floor. It
is reporting how text wraps, not a layout deviation. Mobile passes only because
its slope is ~62px/pair against desktop's ~16px, buying 743px of explained range
to hide the same noise behind. **This revises the earlier entry in this log:** the
"residual band ~80–105px" recorded there is the wrap floor, not layout signal.

same idea at both widths: *two cards with the same amount of data should be the
same height.*

- `floorPx` — worst height spread among cards with identical `u` in that state.
- `floorRatio`, `unfittable` — the best ratio ANY model in `u` could reach here.
- `atNoiseFloor` — the residual is at or under the floor.

- **UNFITTABLE** replaces the bare "UNRELIABLE … no layout signal here" and
  states the two numbers, so the claim is checkable and nobody tries to rescue
  it with `LAYOUT_RESIDUAL_BUDGET_PX`.

## Reverted to worstGroupPx — and two false alarms it exposed

User decision. The tracked statistic is the worst tie group again, so the number
a row PRINTS and the number the comparison DIFFS are one quantity, identical to
the one the fit-impossibility floor uses. No deploy.

`worstGroupPx` is read first by `_cmp_value`, ahead of `spreadPx`: reports
written during the brief largest-group window carry `spreadPx` meaning something
else, and diffing those against a current report would compare two different
quantities and call the difference movement. Both eras carry `worstGroupPx` and
it means one thing in both — verified live by comparing a post-revert run against
a largest-group-era report: `identicalContentSpread unchanged`, correctly.

`largestGroupPx` is still emitted and printed when the two disagree, because
disagreement is informative: it says a small group is straddling the extremes.

### False alarm 1 — the row contradicted itself in consecutive clauses

mlb mobile printed **"AT ITS NOISE FLOOR (164px), so this is text wrap, not
layout deviation"** and then **failed the run** with "LAYOUT RESIDUAL OVER BUDGET
(164px > 150px)" on that same number. No model beats its own floor by
construction, so the budget was unmeetable and the harness would have sat
permanently red on a healthy board — the outcome `fitGroup`'s own comments argue
against. A residual at its floor is now reported and not failed.

### False alarm 2 — "content-independent" inferred from a flat slope

With mobile fixed, mlb **desktop** failed instead: `LAYOUT SPREAD OVER BUDGET
(313px > 150px) with content not driving height`. But identical-content cards
differed by only **70px** on that same reading — 243px of the 313px tracked the
33-57 pair range.

The branch inferred "content is not driving height" from a near-zero linear
slope. On desktop that inference is FALSE, and this log already established why:
the pair grid wraps, so content drives height non-linearly. A flat slope means
the LINE cannot see it, not that it is absent.

The budget is now applied to the content-CONTROLLED figure — cards carrying the
same data, how far apart are they — whenever tied cards exist. Where nothing
ties there is no control, so the raw spread remains the signal and still fails;
the row says which of the two it used. The tie floor is taken from the model's
OWN state, since a floor from a different state is not a control for this one.

## The mlb mobile 151px failure is a FALSE ALARM — the line is curved, not the card

### Hypothesis falsified

There is no outlier. The residuals are U-shaped across pair count:

    u=45  +76      u=49  -2 / -10 / -42      u=53  -41 / -75      u=57  +73

### The mechanism

Per-pair height cost, same element, same width, same instant:

| state | steps | shape |
|---|---|---|
| **Preview** | 62.4 → 62.1 px/pair | **linear** |
| **Live** | 41.3 → 61.8 → 76.6 px/pair | **convex** |

The curvature lives entirely in `section.cards-panel.is-active >
div.cards-overview-grid` (Live: 3187 → 3906px across the series; every sibling
block is flat or moves ≤28px). Live cards put cells of differing heights into a
wrapping grid whose rows take the height of their tallest cell, so each added
pair costs more than the last. Preview cells are uniform, so Preview is linear.
Same grid, same width — the state is what differs.

### Why the harness failed on it, and why that is the harness's fault

    fitRatio 0.2  ->  reliable: True        residualSpread 151  ->  OVER BUDGET

`fitRatio = residual / explained` **cannot see curvature.** A misspecified model
with a wide explained range (771px here) passes the reliability bar and then
trips the budget with a structured residual. `reliable` is measuring the wrong
thing.

And the failure names a card that cannot support the claim:

- worst card is **u=45**, and it is the **only** card at u=45 — it has no
  same-content peers, so "+79px off the model" is deviation from a LINE, never
  from a peer.
- The cards that DO have peers agree to **40px** (Live tie group, u=49, n=4).

So no card is anomalous relative to cards carrying the same data. This is the
same false-alarm family as the two fixed earlier today, surfacing in the
`reliable` branch instead of the `contentIndependent` and `atNoiseFloor` ones.

**Fail on deviation from same-content PEERS, not from the line.** A card is

## fitRatio no longer certifies a curved fit

Lane `ui-probe-curvature-detection`. No deploy.

`fitRatio = residual / explained` is blind to shape by construction: mlb mobile
Live scored **0.20 and `reliable`** while its per-pair cost ran 41.3 -> 61.8 ->
76.6 px/pair. The residual was not noise, it was a bend.

`fitGroup` now tests the shape directly — slopes between consecutive pair-count
group MEANS (means, so within-group wrap noise averages out rather than driving
the sign), then asks whether those slopes drift monotonically. `curved` forces
`reliable: false`, and the row says **MISSPECIFIED**, distinct from UNRELIABLE:
the line is not noisy, it is the wrong shape, and "no layout signal here" would
understate it.

Threshold measured, not guessed, same slate and instant:

    Live    (97.0 - 40.8) / 64.0 = 0.88   curved
    Preview (65.6 - 65.1) / 65.4 = 0.008  straight

## A peer verdict now needs n>=3 cards

Lane `ui-probe-peer-min-group`. User decision. No deploy.

### The reading that prompted it

One run failed at **30.9% > 15.0%** on an **n=2** Live group — 2 cards at 41
pairs, 312px apart on a 1009px card — while the **n=6** group on the same board
sat at **82px**, comfortably under budget. Minutes later there was only **one**
card left at 41 pairs: the pairing was transient. Three consecutive runs after it
were green.

The mechanism is MLB live enrichment reaching the peer rule. The rule assumes
*equal pair count implies comparable cards*; a card still receiving data holds a
TRANSIENT pair count that can coincide with an unrelated card at a different
stage. It was the second time an n=2 group produced a misleading number.

### What changed

`PEER_MIN_GROUP_N = 3` — the smallest n where one odd card is not *itself* the
spread. Groups below it are **reported, never silently dropped**:

    peer deviation in Live NOT JUDGED -- 30.9% over 2 card(s) at 41 pairs,
    below the n>=3 a verdict needs

That wording matters: a thin group over budget is the shape of a transient
pairing, but it is also how a real defect would first appear, so it stays visible.

**`tieFloor` now returns the FULL per-group list**, not just worst and largest.
Without it the gate would have skipped a genuine n=6 group hiding behind a thin
n=2 one whose spread was larger — that case is pinned by
`test_a_thin_group_must_not_mask_a_fat_one`. Reports predating the list fall back
to the summary entry and are still judged; absence of the list is not absence of
a problem.

### Verification

- **91 tests pass** (85 + 6 new): n=2 over budget reports without failing; n=3
  over budget still fails; a thin group does not mask a fat one; the post-churn
  healthy board (n=6 at 82px, n=2 at 51px) stays green; an older report without
  the group list is still judged.
- **Three consecutive live runs: OK**, zero over-budget failures, zero thin-group
  notes, and all four baselined nfl/ncaaf rows `unchanged (baselined)`.

### What this does NOT fix

MLB's identical-content spread is still not baselineable while its slate is live
— it read 81/109/123/164/193/200/312px across the day. This raises the bar for a
verdict; it does not make the underlying number stable. Tomorrow's scheduled
