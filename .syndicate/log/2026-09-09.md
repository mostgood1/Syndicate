### CORRECTION 2026-09-09, later the same day: A CORRECTNESS HOLE IN THE GUARD CORE I WROTE

Found by session `data-mirror-write-guard-sweep`, reproduced here against
`origin/main` (`e44e1d79`) before acting on it.

`_git_ignores` kept a per-DIRECTORY cache beside its per-path one, justified by a
comment I wrote: "a directory rule applies to the whole subtree, so its verdict is
safe to reuse for every sibling." **It is not, and the same file contains the test
that says so.** `git check-ignore` answers NOT ignored for anything in the index
whatever rules match it — that is the entire basis of the exemption, and it means
two different answers coexist inside one directory. A per-directory verdict cannot
express that.

MEASURED, fresh process, real tree, `data/mlb_source/source_artifacts/data/live_lens/`:

    _git_ignores(live_lens_2026_05_29.jsonl)  -> False   correct
    _git_ignores(_probe_never_existed.jsonl)  -> True    correct, and PRIMES the cache
    _git_ignores(live_lens_2026_06_02.jsonl)  -> True    WRONG

One query for an ignored name disarms the guard for every TRACKED file in that
directory for the rest of the process. That directory holds 208 tracked files.

**THE POISONER IS THE GUARD'S OWN SELF-CHECK.** `test_a_tracked_file_is_guarded_
even_inside_an_ignored_subtree` ends on `assert git_ignores(beside) is True` — an
ignored name in that directory — so it primes the cache as its last act and
poisons whatever runs after it in the same xdist worker. It passes alone and
failed in a full parallel run, and that asymmetry was the only signature.

**WHAT THIS DOES AND DOES NOT INVALIDATE.** The failure mode is the guard MISSING
a write, so the write LANDS. Every tree-clean reading in this log was taken with
`git status --porcelain data/ vendor/` returning zero — the filesystem, not the
guard's silence — and a disarmed guard would have shown up as a dirty tree in
exactly those checks. So those readings survive. What the bug does invalidate is
any "the guard reported nothing, therefore nothing wrote" inference; none was
published, and the claim is recorded here so it can be checked rather than taken.

It also gives the `live_lens_2026_06_02.jsonl` mystery its first real mechanism:
an order-dependent exemption keyed on that exact directory produces
dirty-in-one-run / clean-in-the-next while the guard demonstrably fires on the
in-process cases. NOT claimed as the cause — not reproduced — but it beats
"pytest-randomly ordering", which is where both sessions had left it.

**FIX OWNERSHIP, deliberate:** `ba732005` on `session/data-mirror-write-guard-sweep`
deletes the per-directory cache, mutation-checked with the order pinned. I did NOT
write a competing fix — a second version of the same function would force one of
us to discard. Mine to do on top of theirs: reorder the self-check so it does not
END on a priming query, i.e. remove the test's dependency on an implementation
detail of the cache it is supposed to be independent of.
