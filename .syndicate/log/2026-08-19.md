    2024->2025   SP+ r 0.506 resid 17.63  |  PPA r 0.372 resid 18.97

SP+ wins on both metrics in both independent pairs. `SP_RATING_SCALE = 10.0`
calibrated by sweeping the real slate, not derived.

**NCAAF RATINGS WERE LEAKED.** `/ppa/teams?year=S` is season-aggregate and
contains the games being predicted: r 0.663 vs 0.509 as-of over 558 games of
2024, 30% inflation. Fixed to aggregate `/ppa/games` over weeks < N.

**2026 DATA BUILT**, coverage-checked against the 94 FBS teams the wk1 slate
needs: roster 15,442 rows / 138 teams / 0 missing; coach continuity 138 / 0;
returning production 136 / 2 (North Dakota State + Sacramento State, FCS->FBS
transitions with no prior FBS production -- legitimate); transfers 3,288 / 0.

**FIVE OF SEVEN BUILDERS COULD NOT RUN.** Only roster and player_game_stats

**TOTALS: MECHANISM IDENTIFIED.** total = drives x score% x pts/score, and the
decomposition is exhaustive:

    game            total   drives   score%   pts/score   TD share
    LOWEST           27.5    24.4    20.8%      5.43       60.7%
    HIGHEST          68.6    20.0    53.9%      6.35       83.8%

**Scoring rate is the carrier: 20.8% -> 53.9%, a 2.6x swing.** Drives move only
24.4 -> 19.8 (and DOWNWARD as totals rise, which is correct -- scoring drives
burn clock). Real CFB converts ~35-45%; both ends are wrong. TD share 60.7% ->
83.8% against a real ~55-60% is a second defect in the same place.

### BELIEVED, NOT VERIFIED

- That fixing scoring-rate compression fixes totals. The decomposition proves
  scoring rate CARRIES the spread; it does not prove damping it lands total SD
  at 3.46 without moving margins.

### DEAD ENDS -- three failed hypotheses on totals, all reasoned, none measured first

1. **Index clamp too narrow.** Widened [0.05,0.95] -> [-0.75,1.75]. Margins got
   WORSE (15.97 -> 15.27) and totals worse (7.51 -> 9.55). REVERTED.
2. **Yardage weight asymmetry** (`offense*3.0 - defense*2.2`). Swept to parity
   and beyond: total SD moved 7.45..7.83, and parity was WORSE. The refactor
   was kept (constants -> profile fields, NFL byte-identical) but does not fix.
3. **`scoring_environment` weight asymmetry** (`offense*0.18 - defense*0.08`,
   2.25x). Swept 0.18/0.08 down to 0.06/0.06 -- a 3x reduction moved total SD by
   **0.07 points**. REVERTED, including the `profile` parameter it threaded
   through `build_drive_priors`.

**Why all three failed the same way:** they damp INPUTS to a loop whose outputs
COMPOUND. `drive_success_probability` feeds four-down sequences, so a modest
prior change barely moves the converted scoring rate. Correlation among inputs
(the r=0.782 on rating-net-sum) identified what MOVES WITH totals, not what
CREATES them -- decomposition did.

### Two methodology bugs I introduced and then caught, before trusting a
### single calibration number — recorded so they are not rediscovered

1. **A tuple-sort tie artifact.** `sorted(zip(probs, outcomes))` sorts
   ties in predicted probability by OUTCOME as the secondary key. The
   `offset=0` synthetic threshold (line == the player's own rolling mean)
   produces a massive exact-p=0.5 tie cluster, so the naive sort silently
   split that cluster into an all-miss bucket followed by an all-hit
   bucket — a fake 0%-then-100% swing that read exactly like a severe
   calibration defect on the first run. Fixed: sort on probability only.
2. **A pooled-market denominator**, the exact trap `learnings.md`
   2026-08-13 already names. First version of section 2 pooled all 9
   markets into one set of deciles; different markets have structurally
   different probability distributions, so the pooled curve swung sign
   bucket to bucket with nothing a reader could act on. Fixed to report
   per-market, kept a pooled table only as an explicitly labeled
   "informational only" summary.

# 2026-08-19 (~18:5x-19:0xZ) — `soccer-model-dispersion`: `pace_seconds_per_event` sourcing attempted, failed its own cheap falsifier — NOT wired, NOT committed

While the 9-league re-run backtest was in flight, picked up the last
genuinely-unsourced input field per the checklist (`state.md`'s own
"Only `pace_seconds_per_event` remains unsourced" note).

## What was tried

ESPN's boxscore (same `fetch_match_summary` call already made for
possession/set-piece/availability) carries per-team `totalPasses`,
`totalShots`, `totalTackles`, `totalCrosses`, `totalLongBalls`, `wonCorners`,
`foulsCommitted` -- confirmed present on a real sample fixture. Built a proxy:
sum all seven stats across both teams, divide a fixed 5400s (90 min) by that
total, one value per match (`_derive_pace_seconds_per_event` in a throwaway
`espn_match_stats.py` extension, not committed).

## Prototyped on eredivisie first (same discipline as availability)

252 real matches, 8 monthly windows spread 2023-2025 (not one narrow slice):
mean 4.88s, range 3.63-10.71s, stdev 0.50, only 3 rows missing.

## VERIFIED, with evidence -- and it's a clean kill, not an inconclusive result

**Two independent problems, either one disqualifying on its own:**

1. **Scale mismatch.** The engine's `_pace_values` maps `pace_seconds_per_event`
   to `pace_index` via `(13.5 - pace_seconds) / 5.0`, clamped to [-1, 1] --
   13.5s is implicitly the assumed neutral center. The proxy's mean (4.88s)
   is ~2.8x faster than that center; nearly every match would compute an
   index of `(13.5-4.88)/5 = 1.72`, clamped to a CONSTANT +1.0. That is not
   real variation reaching the engine, it is a degenerate ceiling -- worse
   than the current flat 12.0 default in one respect: it would look wired
   while carrying no actual signal. Worth stating plainly: `_pace_values`'s
   13.5/5.0 constants were never calibrated against real data either, since
   this field has NEVER been populated before now -- nobody chose 13.5s
   knowing what real matches look like.
2. **No correlation with the outcome it should plausibly predict, even
   before worrying about rescaling.** Pre-registered hypothesis: faster pace
   -> more chances -> more goals. Measured: `pearson(pace, total match
   goals) = 0.0757`, `t = 1.201` (need ~1.98 for significance at n=252).
   Pace terciles on mean total goals: fast 2.905, mid 2.964, slow 2.952 --
   flat, no monotonic trend. `pearson(pace, |goal margin|) = 0.0079`,
   effectively zero.

## Decision, and why it stops here

**Stopped before the expensive path** (9-league ESPN fetch + pooled OLS +
paired backtest -- the same pipeline possession/set-piece/availability all
went through, each taking real wall-clock hours). This is the identical
"cheaper falsifier first" principle already used once this session for the
Monte-Carlo sim-count check on the original dispersion hypothesis, applied
here to a sourcing question instead of a weight question. A single-league
correlation against the most basic plausible outcome is the cheap version of
the same pooled-regression test the other three fields passed through --
this one failed it outright, at n=252, well before reaching the 9-league
pooled fit's own significance bar.

**Extraction code NOT committed.** Unlike possession/set-piece (kept despite
a non-significant paired test, on the strength of being real infra with no
evidence of harm), this field has no evidence of a real relationship at all
-- committing unwired, unused extraction code would be dead weight, not
infrastructure. `espn_match_stats.py` is unchanged in the shipped tree; only
this log entry and the corresponding `state.md` note persist the finding, so
nobody re-runs the identical experiment.

## Dead ends / near-misses, and why

- Considered rescaling the proxy (linear transform to match the engine's
  13.5s-centered scale) before testing correlation. Decided against doing the
  rescale FIRST -- rescaling a signal that has zero measured relationship to
  the outcome it should predict does not create a relationship, it only
  relocates a null result to different units. Correlation-tested the RAW
  proxy first; the null result would not have changed under any linear
  rescaling (Pearson correlation is scale-invariant), so the rescale step
  was correctly skipped rather than performed and then found not to help.
