### ADDENDUM — the byte-size arithmetic I used to bound the `deploys.md` loss was the wrong instrument

**MEASURED on a directly analogous case, same file, same workflow, hours later.**
The `deploys.md` working copy was dirty again when this checkpoint tripped the
same guard: **1,373,373 B against HEAD's 1,349,295 — 24,078 B of local appends.**
This time it was SAVED byte-exact before being overwritten, so the question that
was unanswerable the first time could be asked:

    sections only in the saved local copy : 0
    non-blank lines nowhere on origin/main: 0

**A file 24 KB larger than HEAD contained NOTHING unique.** The delta is content
that is already upstream, sitting at different offsets — a session appending
locally what it had already landed from its worktree.

**So the bound I put on the earlier loss (`9,059 B` residual, from
`23,737 - 14,678`) measures the wrong thing.** Size delta is not unique content;
the two are only equal if appends never duplicate what upstream already has, and
this measurement shows they routinely do. The honest restatement: the earlier
residual is an UPPER BOUND on bytes, not an estimate of lost information, and the
one directly comparable case measured **0** unique lines. That does not prove the
earlier 9,059 B was also non-unique — I destroyed it before it could be asked —
but it moves "likely superseded draft prose" from a guess about a pattern to an
inference from a measurement of the same pattern.

**The rule that generalises:** to size a loss, diff CONTENT, not bytes. I reached
for the number I could still compute after the fact rather than the number that
answers the question, and then reported it as though it answered the question.
